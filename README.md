# ドカン！お祈りメールクラッシャー

就活の「お祈りメール」やライブの落選メールでモヤっとした気持ちを、ゲームでスカッと発散するアプリです。

## ターゲット

- 就活のお祈りメールをもらってモヤっとしている学生
- ライブの抽選に落選してモヤっとしている学生

## 利用環境

モバイルブラウザ

## 遊び方の流れ

1. **タイトル画面**
   - タイトルが表示される
   - モヤっとしたメールの文章を貼り付ける入力フォーム（アプリ連携ではなく直接コピペ）
   - 「スタート」「遊び方」などのボタン
   - 「スタート」を押すとゲーム画面に移動
2. **ゲーム画面**
   - 入力したメールの文字が1文字ずつブロックに描かれ、壁のように積み上がっている
   - ポケモンGOのボール投げのように、球をブロックに投げつけて崩していく
   - 奥行き（3D演出）を出すかどうかは実装しながら判断

## 画面遷移とメール本文の受け渡し

```
TITLE → 「スタート」 → MAIL_INPUT → 「ゲーム開始」 → GAME
```

- `src/scenes/MailInputScene.js` がメール本文入力画面。ブロックの生成は一切行わず、
  入力文字列をトリムしたものを `onStartGame(mailText)` で渡すだけに徹している。
- `src/main.js` の `App.goTo()` が `onStartGame` の戻り先として
  `GameScene.setMailText(mailText)` を呼んでから `mount()` する
  （`ResultScene.setScore()` と同じ「mount前にsetterで値を渡す」パターン）。
- `GameScene._setupTower()` が実際のブロック生成場所。積む行は
  `_buildRows()` が返す「行（文字配列）の配列」に一本化してあり、`this.mailText` が
  未設定（`null`）の場合（「遊び方」から直接ゲームへ進んだ場合など）もランダムな
  文面を同じ手順で行分解する。つまり「1文字=1ブロック」の経路は常に1本だけ。

### 改行・空白・折り返しの扱い

`GameScene._splitIntoRows()` が行の組み方を1箇所に集約している。

- メール本文中の改行はそのまま新しい行の区切りとして扱う（改行が入るたびに
  タワーの新しい行になる）。
- 改行のない長い行は自動で折り返す。折り返し幅（1行の最大文字数）は
  総文字数の平方根に基づいて決めており、`MAX_ROWS`（現在6行）を超えて
  積み上がりそうな文字数になったら、行数を増やさず折り返し幅（列数）だけを
  増やして横に広げる。
- 行内のスペース（半角/全角）はブロックにしても意味がないため取り除く
  （句読点はそのままブロックになる）。分割は絵文字などのサロゲートペアを
  割らないよう `Array.from()` を使う。
- 全行を折り返し幅と同じ列数に揃え、文字が足りない行は右側を空白ブロック
  （文字なしの`Block`）で埋めている。行ごとに実際の文字数で中央寄せすると、
  短い行の上に長い行が乗ったときに支えのないオーバーハングができて自重で
  崩れてしまうため（実機で確認済み）、必ず全行同じ列数・左詰めで配置している。
- `MAX_MAIL_BLOCKS`（現在100文字。MailInputScene側の`MAX_MAIL_LENGTH`と
  揃えてある）を超える入力は先頭から切り詰めてタワーが大きくなりすぎないように
  している（空白ブロックの分はこの上限に含めない）。

## ブロックの文字表示

ブロックに書かれた文字は DOM のオーバーレイではなく、`CanvasTexture` として
ブロックの面そのものに焼き込んでいる（`src/game/Block.js` の
`createCharacterTexture()`）。文字がメッシュの一部になるため、ブロックが崩れて
回転しても文字が追従し、手前のブロックが奥の文字を正しく隠す。

- 文字を貼るのは手前(+Z)と背面(-Z)の2面のみ。残り4面は紙の断面色。
  `BoxGeometry` のマテリアル配列は `[+X, -X, +Y, -Y, +Z, -Z]` の順。
- 同じ文字のテクスチャは `GameScene` の `characterTextures` で使い回している。
  ブロック間で共有しているので `Block.dispose()` では破棄せず、
  `GameScene.unmount()` でまとめて破棄する。
- テクスチャの解像度（448x288）はブロック手前面の縦横比 1.4:0.9 に合わせてある。
  ブロックの実寸（`GameScene.BLOCK_WIDTH`/`BLOCK_HEIGHT`）を変えるならこの比率も
  一緒に直さないと文字が潰れる。

### 次に触るべき場所（ゲーム担当者向け）

- ゲーム画面のブロックは「紙」の見立て（クリーム色の下地＋墨色の文字）で、
  タイトル画面の背景（`src/game/TitleBackground.js`）のレンガ調とは配色が別。
  世界観を統一するかは未対応。
- タイトル背景のレンガは今も DOM ラベル（`.brick-label`）方式のまま。
  ダミー文字なので実害はないが、ゲーム画面と同じテクスチャ方式に揃える余地はある。
- `HOWTO`（遊び方）からゲームへ直行する導線は残っており、その場合はメール本文が
  ないのでランダム文面が積まれる。`HOWTO → MAIL_INPUT` に変える案は未着手。
- タワーの行・列構成は `GameScene._splitIntoRows()` を参照（改行・折り返し・
  空白パディングの節も参照）。ブロック自体のサイズ（`BLOCK_WIDTH`/`BLOCK_HEIGHT`）は
  文字数によらず固定で、代わりにカメラ距離をタワーの実サイズと画面のアスペクト比
  から動的に計算している（`GameScene._applyCameraFraming()`）。一度、文字数に応じて
  ブロック自体を縮小する案も試したが、カメラを引いた分と相殺してかえって
  読みにくくなることを実機で確認したため、現在の方式（ブロック固定＋動的カメラ）に
  落ち着いている。
- カメラ距離の計算はスマホの縦画面・PCの横画面どちらでもタワー全体が画面に
  収まるよう、`window.innerWidth/innerHeight` のアスペクト比から必要な距離を
  逆算し、画面回転時（`_onResize`）にも引き直している。カメラが見下ろす角度に
  なっている分、正確な視野角計算ではないため `CAMERA_FRAME_PADDING` で余裕を
  持たせてある（詰めるならここが調整のしどころ）。
- ブロックサイズは固定のため、文字数が増えても当たり判定の大きさは変わらない
  （体感難易度への影響は小さいはず）。パドルサイズやボール速度などのゲーム
  バランス調整は今回のスコープ外。
